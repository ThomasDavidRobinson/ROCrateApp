In preparation for the assessment I got a Claude Code subscription and looked online for specification templates. My main goal at this point was to understand what time constraints I would reasonably have, and how best to spend the hour of given time. I also had not written a specification for an agentic LLM, so I searched for some templates and read an article or two regarding that, landing on a template that seemed appropriate. 

Prior to undertaking the assessment I wrote a specification for a separate project, to ensure that everything was working correctly. This specification was quite simple and took the agent about 20 minutes to complete.

My overall plan was to instruct the agent to develop the app from the provided specification, review the code as generated and assess from there.  This seemed to be the consensus of usage patterns I observed online during my research. I found reviewing the generated code to be a little overwhelming, in part due to the time pressure of the assessment and wanting to allow the agent to continue with other tasks. I did not find that I needed to correct the agent during the initial stage of code generation. However, I did not that the agent was trying to find versions the ro-crate and pdf-lib libraries that were already compiled for the browser. I interrupted and instructed the agent that serving the application via node was acceptable. My wording in the specification "simple HTML and JavaScript application" and "No backend or database is necessary" are the likely causes of this behavior. I hadn't really factored this in as a potential issue as my usual workflow is to run everything in a node-alpine container.

I had not observed any code that required my intervention at this point & wanted to demonstrate this process, so I interrupted the agent & instructed it to include some additional fields that the RO-Crate specification states a file entity SHOULD have. The agent had no issue with this and the generated code fit the required function. For a change of this complexity I imagine that this is an acceptable method to go about it, though I would expect that anything more complex would require a more detailed request, or to update the specification. 

Once the agent had built & served the app I noted that the system file browser didn't show the pdf files, only folders - I'm not very familiar with the file browser API off the top of my head so it seemed like the best approach here was to provide context as to _why_ this was an issue, and ask for recommendations. The provided recommendations were quite similar, so I chose the one that felt more user friendly to me. 

I think the main change I would make to given the opportunity to do the assessment again would be to move the criteria described in the acceptance criteria & failure state sections to be a part of the functional requirements. Then write a more deliberate test regime for the agent to conduct following code generation. I would also dedicate more time to describing the UI elements and visual flow of the application too. 

In comparison to a prompt by prompt approach I can definitely see the significant time and quality advantages an agent has. I had felt that this methodology would be a very hands off, separated experience but having completed the assessment I feel like I would be able to spend much more time polishing and refining the application. 

I think the main strength of using an agent for this kind of task is to get a high quality prototype off the ground within a very short period of time. I think the addition of skills or MCP would improve this process significantly. The main limiting factor that I observed is that the agent will fill in gaps in the specification by itself, and that it may take things like "no backend is necessary" and take that as "don't use node to serve the app". Both of these limitations can be overcome quite easily by writing a more robust specification and providing the agent a better environment. 

Thanks for the opportunity to complete the assessment and learn something new :)
